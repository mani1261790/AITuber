# 2026-10-19の保護停止は使用量カウンターの誤計上

## 特定結果

CloudflareやChatGPTの利用枠切れではなく、追加したStorageBudgetの書き込み上限20,000行への誤到達だった。

本番の停止応答は「無料枠を保護するため、本日の処理を停止しました」。これはアプリ独自のStorageSafetyLimitが返す文言。管理者認証付き診断経路を追加し、停止中の実データを取得した。

| 指標 | Cloudflare集計（20:19 JSTまで） | 保護カウンター（20:20 JST取得） |
| --- | ---: | ---: |
| 読み取り行 | 17,679 | 194,000 |
| 書き込み行 | 4,918 | 20,000 |
| DO呼び出し | 771 | 19,500 |

`exceeded`は`writes`だけだった。Cloudflare集計とアプリSQLカウンターは完全に同じ集計範囲ではないが、実際のプラットフォーム使用量よりはるかに大きい保存値と、下記の再現結果から誤計上を確定した。

## 原因

SQL読み取り1,000行、SQL書き込み100行、リクエスト100回単位で先に予約し、異常終了時の未記録分を保守的に見込む設計だった。しかし、正常終了するflushも予約量を保存し、実測値に戻していなかった。

次の起動は未使用の予約分を実使用と扱って再開し、さらに切り上げる。普通の待機・復帰でも累積するため、少ない処理で保護上限に達した。ローカルで「1リクエスト→正常終了→再起動」の繰り返しと「10行読み取り・1行書き込み→正常終了→再起動」を再現すると、修正前はどちらも誤停止した。

## 修正と補正

- 正常終了のflushは実測値を保存する。処理途中の異常終了に備える予約は維持。
- 初期化前でも、管理者だけがカウンターを読み取れる診断経路を追加。停止状態の調査に教材データの読み込みは不要。
- アプリの停止は`storage_safety_stop`、Cloudflare側は`storage_quota_exceeded`と区別。管理画面は両方で自動更新を停止する。
- 実測と照合できた2026-10-19の保存値（194,000 / 20,000 / 19,500）に完全一致する場合だけ、一度補正。
- 補正後は読み取り50,000、書き込み10,000、リクエスト2,000。実測の2倍以上を確保し、ゼロリセットや上限引き上げはしていない。
- 元の保存値・補正値・Cloudflare集計のActions IDをDO内に保存。別の値・別の日は補正しない。
- 停止した生成や講義を自動再開しない。
